# Sprint 057: Collection Schedule Domain and Persistence Foundation

## Goal

Add the Collector Runtime-owned `CollectionSchedule` aggregate as a strict
domain model with PostgreSQL persistence and three application use cases
(upsert, get, list). The current collector only supports manually requested
collection runs (trigger type `MANUAL_API`); there is no persisted schedule
and no automatic dispatcher. This sprint lays the persistence and validation
foundation that future dispatch work will build on.

This sprint does not implement a scheduler process, due-schedule claiming,
run generation, a `SCHEDULED` trigger type, worker changes, browser
changes, HTTP changes, Web UI changes, CLI changes, Docker changes, or
notification changes.

## Scope

### Domain — `src/collector-runtime/domain/`

- `collection-schedule.schemas.ts` (new): `CollectionScheduleSchema`
  (`.strict()`), `CollectionScheduleIsoDateTimeSchema`,
  `CollectionScheduleSourceGroupIdSchema`, and
  `CollectionScheduleIntervalMinutesSchema` (integer 1..10080).
  `parameters` reuses the existing `CollectionRunParametersSchema` from
  `collection-run.schemas.ts`.
- `collection-schedule.ts` (new): re-exports `infer` type aliases.
- `validation.ts` (modified): add `validateCollectionSchedule` and
  `validateCollectionScheduleParameters`.
- `index.ts` (modified): re-export the new schema and type modules.

### Application — `src/collector-runtime/application/`

- New port `CollectionScheduleRepository` with `upsert`,
  `findBySourceGroupId`, and `list`. Identity is `sourceGroupId` (no
  separate id).
- New `UpsertCollectionScheduleInput`, `CollectionScheduleListQuery`, and
  `CollectionScheduleListResult` (with exact `total: number`).
- New use cases: `UpsertCollectionScheduleUseCase`,
  `GetCollectionScheduleUseCase`, `ListCollectionSchedulesUseCase`.
- New validation helpers in `collection-schedule-validation.ts`
  (`toCollectionScheduleIsoDateTime`,
  `loadValidatedCollectionScheduleBySourceGroupId`,
  `validateCollectionScheduleForApplication`,
  `validateCollectionScheduleParametersForApplication`).
- New `InMemoryCollectionScheduleRepository` in `test-support/`.
- New schedule-specific errors in `application-errors.ts`:
  `CollectionScheduleValidationError`,
  `CollectionScheduleNotFoundError`,
  `CollectionScheduleSourceGroupNotFoundError`,
  `CollectionScheduleSourceGroupNotActiveError`,
  `CollectionScheduleSourceGroupPlatformUnsupportedError`.
- Application `index.ts` (modified): re-export new modules.

### Persistence — `src/infrastructure/database/`

- `schema/collector-runtime.schema.ts` (modified): new
  `collector_collection_schedules` table with `source_group_id` as primary
  key, `enabled`, `interval_minutes`, `next_run_at`, JSONB `parameters`,
  `created_at`, `updated_at`, interval `CHECK` constraint
  (`interval_minutes BETWEEN 1 AND 10080`), and composite index
  `collector_collection_schedules_due_idx` on
  `(enabled, next_run_at, source_group_id)`. No foreign key to Content
  Manager.
- `mappers/collector-runtime.mapper.ts` (modified): add
  `CollectionScheduleRow` / `CollectionScheduleInsert`,
  `InvalidPersistedCollectionScheduleRecordError`,
  `toCollectionScheduleRow`, and `toCollectionScheduleDomain`. Export
  `normalizeIsoDateTime` so the schedule mapper can reuse it.
- `repositories/drizzle-collection-schedule.repository.ts` (new):
  implements the port. `upsert` uses raw SQL with
  `INSERT ... ON CONFLICT (source_group_id) DO UPDATE SET ... RETURNING *`
  so the persisted `created_at` is preserved and `updated_at` is bumped.
  `findBySourceGroupId` uses typed query. `list` orders
  `next_run_at ASC, source_group_id ASC` and returns exact `total`.
- `index.ts` (modified): re-export the new repository.
- New migration under `drizzle/` (generated by drizzle-kit).

### Composition — `src/composition/collector-runtime/`

- `collector-runtime.container.ts` (modified): add
  `collectionSchedules: CollectionScheduleRepository` to dependencies and
  the three new use cases to the container.
- `create-collector-runtime.ts` (modified): wire
  `DrizzleCollectionScheduleRepository` into
  `createCollectorRuntimeFromDatabaseClient`.

### Documentation

- `docs/SPRINTS/active.md` (modified): Sprint 057 active, Sprint 056
  recorded as accepted.
- `docs/modules/collector-runtime.md` (modified): add
  `CollectionSchedule` aggregate ownership note.

## Architecture Boundaries

- Domain code depends only on Zod and the existing `CollectionRunParametersSchema`.
  No HTTP, Fastify, PostgreSQL, Drizzle, browser, queue, or React imports.
- Application code owns the repository port and uses the existing
  `SourceGroupLookupPort` for source-group validation. No Drizzle imports
  in application code.
- Cross-module communication uses the existing `SourceGroupLookupPort`
  (Content Manager HTTP client); no new ports and no foreign keys to
  Content Manager tables.
- Upsert preserves persisted `created_at` and bumps `updated_at`. No
  cross-aggregate side effects.
- Strict Zod schemas (`.strict()`) and validation at every layer
  boundary. Null-vs-omission semantics preserved.

## Out Of Scope

- Scheduler process or polling loop.
- Due-schedule claiming or atomic claiming.
- Collection-run generation or any `SCHEDULED` trigger type on
  `CollectionRun`.
- Worker, browser, HTTP, Web UI, CLI, Docker, notification, retry,
  catch-up, or bulk behavior.
- Content Manager persistence changes.
- Cross-module foreign keys.
- Commits or pushes.

### Test coverage targets

- Domain: schema rejects out-of-range interval (0, 10081), missing
  fields, non-ISO datetime, and missing fields; accepts valid payload.
- Application: upsert happy path; upsert preserves `created_at` and bumps
  `updated_at`; upsert rejects `enabled=true` for non-ACTIVE source group;
  upsert allows `enabled=false` for PAUSED/ARCHIVED Facebook groups;
  upsert rejects non-Facebook platform; upsert maps 404 lookup to
  `CollectionScheduleSourceGroupNotFoundError`; upsert maps unexpected
  lookup failure to `SourceGroupLookupFailedError`; upsert input
  validation covers empty sourceGroupId, interval bounds, ISO datetime,
  and parameter schema; get by sourceGroupId; get not-found; list empty;
  list deterministic ordering (`next_run_at` ASC, `source_group_id` ASC
  tiebreaker); list exact total independent of paging; list rejects bad
  limit/offset.
- Mapper: valid row round-trip; invalid persisted row throws
  `InvalidPersistedCollectionScheduleRecordError`.
- Drizzle integration (against migrated DB): upsert inserts when absent;
  upsert updates and preserves `created_at`; `findBySourceGroupId`
  returns null/row; list ordering and exact total.

## Sprint Status

Sprint 056 is accepted and recorded as the operator authentication
health filtering and profile inventory pagination foundation. Sprint 057
is implemented as the `CollectionSchedule` domain and persistence
foundation. It provides the strict domain model, PostgreSQL table,
in-memory and Drizzle repositories, three use cases, validation helpers,
schedule-specific errors, and composition wiring needed for a future
sprint to introduce a scheduler, due-schedule claiming, and run
generation. It does not advance beyond its declared scope.
